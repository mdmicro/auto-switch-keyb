# Вклад в проект

Небольшие правила, чтобы правки легко вливались.

## Общие принципы

- Проект — Windows-only, Python 3.9+. Никаких новых зависимостей без причины:
  текущий набор — `pywin32`, `pystray`, `Pillow` + stdlib (`tkinter`).
- Приложение не имеет права обращаться в сеть. Патчи с сетевыми вызовами
  не принимаются (см. README, раздел «Безопасность»).
- Логика исправления живёт в `engine.py`/`corrector.py`/`fixer.py`; UI
  (`tray.py`, `settings.py`) — наблюдатель, логику в него не добавляем.
- В колбэке хука (`_on_key`) — никакого файлового I/O и тяжёлых вызовов:
  только очередь (`self._fix_logs`) и быстрые проверки.

## Стиль

- PEP 8, строки ≤ 100 символов (в `fixer.py` допускаются длинные
  объявления структур — так читаются таблицы C-API).
- Комментарии и docstrings — на русском (проект русскоязычный), код-идентификаторы
  на английском.
- Кодировка всех `.py` — UTF-8 с `# -*- coding: utf-8 -*-`.
  ⚠️ `.ps1` — только ASCII: Windows PowerShell 5.1 читает файлы без BOM в
  OEM-кодировке, не-ASCII ломает парсинг.

## Тесты

- Перед PR: `py -3.10 test_engine.py` и `py -3.10 test_corrector.py` — обязаны
  быть зелёными.
- Изменения в хуке/фиксере сопровождаем тестом из `test_engine.py` (моки
  `replace_last_word`/`switch_layout`) — e2e-скрипты в `AppData\Temp` для
  ручных проверок, в CI они не гоняются (шлют реальный ввод).
- Мелкие правки UI можно не тестировать автотестами — опишите в PR, что
  проверяли вручную.

## Структура коммита

- Один логический change на коммит; сообщение — «что и зачем», не «как».
- Не коммитим: `dist/`, `build/`, `*.onefile-build`, `nuitka-crash-report.xml`,
  `__pycache__/`.

## Баг-репорты

Желательно: версия (EXE/исходники), шаги, лог из
`%LOCALAPPDATA%\auto-switch-keyb\log.txt` (последние строки), приложение,
где воспроизводится.
